ShelfVisor 구조적/보안적 예상 취약점 정리
작성 기준: 데모 버전 이후, OpenCV 책등 검출, OCR 연동, 결과 저장, 여러 이용자 사용을 어느 정도 구현한 상태

1. 이미지 업로드 관련 위험

- 사용자가 실제 이미지가 아닌 파일을 이미지처럼 위장해서 업로드할 수 있다.
- 손상된 이미지, 비정상 메타데이터, 매우 큰 해상도의 이미지가 서버 메모리를 과도하게 사용할 수 있다.
- 압축률이 비정상적으로 높은 이미지가 디코딩 과정에서 큰 메모리를 요구할 수 있다.
- 원본 파일명을 그대로 저장하면 경로 조작, 파일 덮어쓰기, 로그 오염 문제가 생길 수 있다.

권장 대응:
- MIME 타입만 믿지 말고 실제 이미지 디코딩 검증을 수행한다.
- 허용 포맷을 JPEG/PNG/WebP 등으로 제한한다.
- 파일 크기뿐 아니라 최대 픽셀 수, 최대 가로/세로 길이를 제한한다.
- 업로드 후 서버에서 안전한 포맷으로 재인코딩한다.
- 저장 파일명은 UUID 기반으로 생성하고, 원본 파일명은 메타데이터로만 보관한다.


2. OpenCV 이미지 분석 처리 부하

- 책등 경계 검출은 이미지 크기와 알고리즘에 따라 CPU 사용량이 크게 증가할 수 있다.
- 여러 사용자가 동시에 이미지를 업로드하면 API 서버가 분석 작업에 묶여 응답이 느려질 수 있다.
- 특정 이미지에서 contour 탐색, threshold, morphology 처리 등이 예상보다 오래 걸릴 수 있다.
- 분석 로직이 API 요청 흐름 안에서 바로 실행되면 장애가 전체 서비스 응답 지연으로 이어질 수 있다.

권장 대응:
- API 서버와 분석 워커를 분리한다.
- 업로드 요청은 분석 작업 ID를 반환하고, 결과는 별도 조회 API로 확인하게 한다.
- 분석 작업별 타임아웃을 둔다.
- 워커 동시 실행 수를 제한한다.
- 이미지 리사이징/전처리를 먼저 수행해 분석 입력 크기를 통제한다.


3. OCR 연동 및 비용 폭주 위험

- Google Cloud Vision 같은 외부 OCR API는 호출량에 따라 비용이 증가한다.
- 인증 없이 공개된 분석 API는 자동화된 대량 요청에 악용될 수 있다.
- 같은 이미지가 반복 업로드되면 동일 OCR 비용이 중복 발생할 수 있다.
- OCR API 장애나 지연이 전체 분석 흐름을 막을 수 있다.

권장 대응:
- 로그인 또는 API 키 기반 사용자를 구분한다.
- 사용자별/기관별 일일 분석 횟수와 OCR 호출량을 제한한다.
- 이미지 해시를 이용해 중복 분석 캐시를 검토한다.
- OCR 호출 실패 시 재시도 횟수와 백오프 정책을 둔다.
- OCR 비용 모니터링과 예산 알림을 설정한다.


4. 개인정보 및 민감정보 노출

- 서가 사진에는 이용자 얼굴, 직원, 위치 정보, 도서관 내부 구조, 관리 라벨 등이 포함될 수 있다.
- OCR 결과에 청구 기호 외의 개인정보나 내부 메모가 포함될 수 있다.
- 원본 이미지와 결과 이미지를 장기간 저장하면 개인정보 보관 리스크가 커진다.
- 분석 이력 화면에서 다른 사용자의 이미지나 결과가 노출될 수 있다.

권장 대응:
- 원본 이미지 보관 여부와 보관 기간을 명확히 정한다.
- 필요하지 않으면 원본 이미지는 분석 후 즉시 삭제한다.
- 결과 이미지도 자동 만료 정책을 둔다.
- 사용자/기관 단위 접근 권한을 엄격히 분리한다.
- 로그에 OCR 전문이나 이미지 URL을 과도하게 남기지 않는다.
- 필요하면 얼굴 또는 비서가 영역 마스킹을 검토한다.


5. 인증, 권한, 사용량 제한

- 여러 이용자가 사용하는 서비스에서는 익명 업로드가 비용과 장애 위험을 키운다.
- 관리자 기능, 분석 이력, 결과 다운로드가 생기면 권한 검사가 누락될 수 있다.
- 사용자가 다른 사용자의 분석 ID를 추측해 결과를 조회할 수 있다.

권장 대응:
- 사용자 인증을 도입한다.
- 기관/팀/사용자 단위 권한 모델을 정의한다.
- 분석 작업 ID는 추측하기 어려운 값으로 만든다.
- 결과 조회, 이미지 다운로드, 이력 조회 API마다 소유권 검사를 수행한다.
- rate limit을 IP 기준뿐 아니라 사용자 계정 기준으로도 적용한다.


6. API 구조와 비동기 작업 관리

- `/api/analyze`가 즉시 전체 분석을 끝내는 구조는 실제 OCR/저장 단계가 들어가면 불안정해진다.
- 사용자가 브라우저를 닫거나 네트워크가 끊기면 진행 중 작업 상태 관리가 어려울 수 있다.
- 분석 실패, OCR 실패, 부분 성공 같은 상태를 명확히 표현하지 않으면 운영 대응이 어렵다.

권장 대응:
- `POST /api/jobs`로 분석 작업을 생성한다.
- `GET /api/jobs/{job_id}`로 상태를 조회한다.
- `GET /api/jobs/{job_id}/result`로 결과를 조회한다.
- 상태값을 queued, processing, needs_review, completed, failed 등으로 분리한다.
- 실패 사유와 재시도 가능 여부를 저장한다.


7. 저장소와 데이터베이스 설계 위험

- 원본 이미지, 결과 이미지, OCR 텍스트, 분석 박스 좌표가 서로 맞지 않으면 재현성이 떨어진다.
- 이미지 파일은 스토리지에 있고 메타데이터는 DB에 있을 때 삭제/정합성 문제가 생길 수 있다.
- 분석 알고리즘 버전이 바뀌면 과거 결과와 현재 결과가 달라질 수 있다.

권장 대응:
- 분석 작업마다 알고리즘 버전, OCR 모델/설정, 생성 시간을 저장한다.
- 이미지와 분석 결과의 생명주기를 함께 관리한다.
- 삭제 요청 시 DB와 스토리지 양쪽이 정리되도록 한다.
- 원본 이미지, 전처리 이미지, 결과 이미지의 관계를 명확히 기록한다.


8. 청구 기호 정렬 규칙의 복잡성

- 도서관마다 청구 기호 체계와 배가 규칙이 다를 수 있다.
- 숫자, 문자, 한글, 저자기호, 권차, 복본, 별치기호 등이 섞이면 단순 문자열 정렬로는 오판할 수 있다.
- OCR 오류와 정렬 규칙 오류가 구분되지 않으면 사용자 신뢰가 낮아진다.

권장 대응:
- 청구 기호 파서를 별도 모듈로 분리한다.
- 도서관별 규칙 프로파일을 둘 수 있게 한다.
- 정렬 판단 결과에 근거와 confidence를 함께 제공한다.
- 확실하지 않은 항목은 "오류"가 아니라 "검토 필요"로 표시한다.
- 사람이 청구 기호를 수정하고 재검사할 수 있는 흐름을 둔다.


9. 분석 결과 신뢰성과 사용자 검토

- 책등 경계가 잘못 잡히면 OCR과 정렬 판단이 연쇄적으로 틀릴 수 있다.
- OCR confidence가 낮은데도 자동으로 순서 오류라고 판정하면 업무 혼란이 생긴다.
- 결과 이미지의 박스와 실제 책 위치가 어긋나면 사용자가 현장에서 잘못 조치할 수 있다.

권장 대응:
- 책등 검출 confidence, OCR confidence, 정렬 confidence를 분리해 표시한다.
- 낮은 confidence 항목은 자동 판정 대신 검토 대상으로 분류한다.
- 사용자가 책등 박스와 OCR 텍스트를 수정할 수 있는 리뷰 UI를 제공한다.
- 최종 결과에는 "자동 분석 결과이며 검토가 필요할 수 있음"을 명확히 표시한다.


10. 프론트엔드 보안과 결과 표시

- OCR 결과를 그대로 HTML에 삽입하면 XSS 위험이 생길 수 있다.
- 분석 이력, 공유 링크, 다운로드 기능이 생기면 접근 제어 누락 가능성이 있다.
- 큰 결과 이미지를 반복 표시하면 브라우저 메모리 사용량이 증가할 수 있다.

권장 대응:
- OCR 텍스트는 HTML로 해석하지 않고 텍스트로만 렌더링한다.
- 공유 링크는 만료 시간과 권한 검사를 둔다.
- 결과 이미지는 적절히 압축하고 썸네일을 사용한다.
- 프론트엔드에서 받은 데이터는 신뢰하지 않고 서버에서 다시 권한을 검증한다.


11. CORS, CSRF, 배포 경계

- 공개 API가 되면 다른 웹사이트에서 분석 API를 호출할 수 있다.
- 쿠키 기반 인증을 쓰면 CSRF 방어가 필요하다.
- 프론트엔드와 API 서버가 분리되면 CORS 설정이 과도하게 열릴 수 있다.

권장 대응:
- 허용된 도메인만 CORS에 등록한다.
- 인증 방식에 따라 CSRF 토큰 또는 SameSite 쿠키 정책을 적용한다.
- 운영/개발 CORS 설정을 분리한다.
- 관리자 API는 별도 권한과 접근 제한을 둔다.


12. 로그, 모니터링, 장애 대응

- 이미지 경로, OCR 텍스트, 사용자 정보가 로그에 남으면 민감정보 노출 위험이 있다.
- 분석 실패율, OCR 지연, 비용 증가를 모니터링하지 않으면 장애를 늦게 알 수 있다.
- 워커 큐가 밀릴 때 사용자에게 상태를 제대로 알려주지 않으면 반복 요청이 늘어난다.

권장 대응:
- 로그에는 필요한 최소 정보만 남긴다.
- OCR 전문과 원본 이미지 URL은 기본 로그에서 제외한다.
- 작업 큐 길이, 평균 분석 시간, 실패율, OCR 비용을 모니터링한다.
- 사용자에게 대기/처리/실패 상태를 명확히 보여준다.


13. 배포 및 인프라 위험

- 단일 서버에서 API, 이미지 분석, OCR 호출, 파일 저장을 모두 처리하면 확장성이 낮다.
- 서버 로컬 디스크에 이미지를 저장하면 배포/스케일아웃 시 파일이 사라지거나 분산될 수 있다.
- 개발용 reload 설정이나 디버그 설정이 운영에 남으면 보안 위험이 된다.

권장 대응:
- 운영에서는 reload/debug 설정을 끈다.
- 정적 파일, API 서버, 분석 워커, 스토리지를 역할별로 분리한다.
- 원본/결과 이미지는 S3, GCS 같은 오브젝트 스토리지에 저장한다.
- 비밀키와 OCR 인증 정보는 환경변수 또는 Secret Manager로 관리한다.


14. 권장 목표 구조

브라우저
-> FastAPI API 서버
-> 작업 큐
-> 분석 워커(OpenCV + OCR)
-> 오브젝트 스토리지
-> 데이터베이스
-> 결과 조회 API

이 구조에서는 업로드 요청과 분석 처리를 분리할 수 있고, OCR 지연이나 분석 실패가 전체 웹 요청을 막는 일을 줄일 수 있다.


15. 우선순위 높은 대응 항목

1. 업로드 파일의 실제 이미지 검증과 최대 픽셀 수 제한
2. 분석 API를 비동기 작업 구조로 전환
3. 사용자별 rate limit과 OCR 호출량 제한
4. 원본/결과 이미지 보관 기간 정책 수립
5. OCR confidence와 검토 필요 상태 표시
6. 사용자/기관별 결과 접근 권한 검증
7. 운영 환경에서 reload/debug 비활성화
8. 로그의 민감정보 최소화
